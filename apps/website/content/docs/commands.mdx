## fizz init

<include>../generated/commands/init.md</include>

It runs no fix itself: the fixes need `sudo` or a login. It needs a terminal, and when a config already exists it shows it and changes nothing. After writing a config, it offers a dry run. [Getting started](/docs/getting-started) walks through it.

## fizz ship

<include>../generated/commands/ship.md</include>

A Ship checks every Machine, plans its Steps, asks any Questions, then applies the plans in parallel. The Ledger lists what changes on each Machine by address: `pnpm:vercel`, `repos:t3code`.

### Answering in advance

`--answer kind=choice` answers every Question of a kind: `range=bump|skip|downgrade`, `config=overwrite|stop`, `file=overwrite|skip`, or `skill=overwrite|skip`. `--answer kind:subject=choice` answers one, such as `range:pnpm:vercel=bump`, and wins over the kind's answer.

Without a terminal, a Question is never waited on: a `range`, `file`, or `skill` Question is skipped, and a `config` Question stops the Ship. Piped to a file, the Ledger prints the full list once at the end.

### A different config elsewhere

If another Machine's config was edited there, was never written by a Ship, or was shipped there more recently than this one last reached it, the Ship asks first: use that config here and ship it, overwrite it with this one, or stop. `--overwrite-config` answers overwrite in advance, and without a terminal the Ship stops instead.

## fizz status

<include>../generated/commands/status.md</include>

Each Machine is a column, numbered as the list at the top numbers them: `✓` in line, `↑` the next Ship changes it, `?` the next Ship asks a Question about it, `✗` it fails, `–` skipped, `·` not targeted there, and `○` the Machine was not checked (offline, or no Tailscale SSH). Under the grid, each Machine lists what differs there and why. It plans exactly as `fizz ship --dry-run` does, so it agrees with the next Ship; it never asks a Question and writes no Ship Log.

## fizz logs

<include>../generated/commands/logs.md</include>

Every Ship, dry runs included, writes a Ship Log on the Machine that started it, under `~/.local/state/fleetfizz/logs`, and ends by printing its id: `log: fizz logs 2026-10-18T14-03-22Z-connors-macbook-pro`. Each line has its time, its level, and the Machine and phase it belongs to; lines a Machine printed start with `> `. A Machine keeps its last 20.

## fizz config

<include>../generated/commands/config.md</include>

It reads only the config and the tailnet, so it is instant and works with Machines offline.

### fizz config add

Every `add` writes its entry the way the docs write it, the shorthand (`"gh": "*"`) when it has no Targeting, then prints the lines it changed. It saves the config only when it still loads, and keeps its comments and layout. An Item that is already there is an error; change it with `fizz config edit`. Without a terminal, a missing value is an error instead of a prompt.

## fizz self-update

<include>../generated/commands/self-update.md</include>

It installs that fleetfizz on this Machine with the package manager that installed fizz, then sets the config's `version`, so a version that fails to install leaves the config as it was. The other Machines get it on the next Ship. Every fizz also switches to the config's `version` on its own before it runs a command that reads the config, older or newer, so a Machine that receives a new config catches up on its next command.
