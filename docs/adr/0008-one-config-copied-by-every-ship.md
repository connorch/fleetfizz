# One config at ~/.config/fleetfizz, copied to every Machine by every Ship

The config no longer lives in a repo (ADR 0004). It is `$XDG_CONFIG_HOME/fleetfizz/config.jsonc` (`fleet.config.jsonc` until 0.4.0; the directory already says fleet) (default `~/.config/fleetfizz/`) on every Machine, and a Ship copies the Starting Machine's copy to every reachable Machine as a Step, after the Lent Token on stdin, never in argv. The `machines` map in the config is the Fleet: only the Machines it lists are ever checked or changed, and the Starting Machine must be one of them. fleetfizz is installed with `vp install -g fleetfizz` and pins itself implicitly: a Ship from version X plans `fleetfizz@X` on every Machine that runs a different version, so the whole Fleet converges on the shipper's version. A Machine that runs a newer fleetfizz than the shipper fails its plan ("upgrade here first") rather than being downgraded. A Machine without vp is bootstrapped with vp's installer (`curl -fsSL https://vite.plus | bash`) as its first Step.

Each Machine keeps an Install Record for the config, `~/.local/state/fleetfizz/records/config.json`, beside the Providers' records: `ship`, the Ship that wrote the config there; `sha`, the sha256 of what it wrote; and `reached`, a map from Machine name to the time a Ship of this config last reached that Machine. The config itself carries nothing a Ship writes (until 0.10.0 it carried that map as `shippedAt`, `shippedFrom`, and `shippedTo`, rewritten into the file by every Ship). A Ship builds one record from the Starting Machine's own: `reached[m]` becomes now for every Machine it plans and for the Starting Machine itself, the other entries stay, and Machines no longer in `machines` are dropped. Each Machine's config Step writes that record after the config, so a record says what landed there and what the copy knows about every other Machine. The Starting Machine writes its own before Apply as well, so an interrupted Ship still knows what it shipped, and again after Apply, claiming only the Machines whose config Step completed.

The Check reports every Machine's config, its sha256, and its record. A copy that differs from the Starting Machine's needs a Question when no Ship wrote it (no record), when it was edited there (its sha no longer matches its record: Drift), or when it is stale-protected: its own `reached[X]` is newer than the Starting Machine's `reached[X]`, so a Ship from elsewhere reached `X` after this config last did (this Machine was offline, or `X` was), and continuing would overwrite a newer config with an older one. Otherwise the Ship overwrites it. The Ship asks, and without a TTY it aborts unless `--overwrite-config` answered in advance. One answer is to use that config instead: the Ship writes it over the Starting Machine's file, with a record that knows what both copies knew (each Machine at its newest time) and that it reached this Machine now, and starts over from the Check, since the config decides what is checked. Copies with the same text are one choice, because one Ship from elsewhere leaves the same copy on every Machine it reaches. A single time per Machine was not enough: a Ship that misses `X` would still advance it, and `X`'s newer config would look older on the next Ship. Every copy's record is written before the Ship knows which Machines it will reach, so it claims every Machine the Ship planned; only the Starting Machine's own is rewritten afterwards. A record can therefore over-claim a Machine whose Check succeeded but whose Apply failed. That Machine's config was already checked, and overwriting it was already approved if it was newer, so the next Ship from a Machine holding that record overwrites it without asking again. A second round trip to correct every record was not worth that one skipped re-prompt. The times are not edit timestamps: an edit changes only the sha. A file named by `--config` has no record, so it knows nothing about any Machine: every copy that differs and has a record asks, and the Starting Machine's own copy is checked like any other, its record written only by its own config Step.

## Considered Options

- **Config in the user's repo, fleetfizz as that repo's devDependency (ADR 0004, superseded).** It made that repo special: it had to be cloned and installed on a Machine before that Machine could ship, and `pnpm ship` had to run from inside it. With every repo an ordinary Tracked Repo, the config has to live outside all of them.
- **`~/.config/fleetfizz` as a git clone that the Ship fetches and resets (rejected).** History and conflict detection for free, but it needs a config repo, a remote, and the Lent Token on every Machine just to read the config. The config is one small file; copying it is less machinery, and a user who wants history can keep the directory under git themselves without fleetfizz knowing.
- **One time per Machine (rejected).** A version number or a single "last shipped" time in each record, compared between two Machines. A Ship that cannot reach a Machine still advances the Starting Machine's time, so that Machine's newer config loses its protection on the next Ship; a counter cannot tell "behind" from "edited separately". The per-Machine map is a version vector, and costs one key.
- **The map in the config, as `shippedAt`, `shippedFrom`, and `shippedTo` (superseded in 0.10.0).** It changed the config on every Ship, noise for anyone who keeps it under git, and could not see an edit made on a target: the next Ship from elsewhere overwrote it silently.
- **fleetfizz listed in `globals` by the user (rejected).** A listed version can differ from the binary that read the config; the implicit pin cannot.
- **Downgrade a Machine that runs a newer fleetfizz (rejected).** A newer remote means someone shipped a newer version from there; the shipper is the one behind.

## Consequences

- Every Machine in the Fleet can be a Starting Machine as soon as one Ship has reached it: it has vp, fleetfizz, and the config.
- Amends ADR 0001's prerequisites: a remote Machine needs `tailscaled` with SSH, `git`, `curl`, and a shell. vp is no longer a prerequisite.
- Bootstrapping a new Machine is: enable Tailscale SSH, add it to `machines`, Ship.
- A Ship never rewrites the config; only a bump or an adopted Stale Config does. A dry run writes no record and copies nothing, and reports the staleness as a note.
- The Ledger's `config` line is unchanged where a Machine's copy already matches, and `a1b2c3d → 9f8e7d6` where it does not.
- `fizz logs` finds the last Ship that reached a Machine from its record (ADR 0015).
- `--config <path>` remains for one-off runs; the upward search from the working directory goes away.
- Machines on the tailnet that are not listed are ignored silently, and a listed name that is not on the tailnet is an error, as today.
