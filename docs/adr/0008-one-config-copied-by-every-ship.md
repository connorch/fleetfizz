# One config at ~/.config/fleetfizz, copied to every Machine by every Ship

The config no longer lives in a repo (ADR 0004). It is `$XDG_CONFIG_HOME/fleetfizz/config.jsonc` (`fleet.config.jsonc` until 0.4.0; the directory already says fleet) (default `~/.config/fleetfizz/`) on every Machine, and a Ship copies the Starting Machine's copy to every reachable Machine as a Step, after the Lent Token on stdin, never in argv. The `machines` map in the config is the Fleet: only the Machines it lists are ever gathered or changed, and the Starting Machine must be one of them. fleetfizz is installed with `vp install -g fleetfizz` and pins itself implicitly: a Ship from version X plans `fleetfizz@X` on every Machine that runs a different version, so the whole Fleet converges on the shipper's version. A Machine that runs a newer fleetfizz than the shipper fails its plan ("upgrade here first") rather than being downgraded. A Machine without vp is bootstrapped with vp's installer (`curl -fsSL https://vite.plus | bash`) as its first Step.

The config carries `shippedAt`, `shippedFrom`, and `shippedTo`, a map from Machine name to the time a Ship of this config last reached that Machine. The Ship writes them before anything is copied: `shippedAt` is now, and `shippedTo[m]` is now for every Machine this Ship applies to. Gather reports every remote's config. A remote `X` is stale-protected when its own `shippedTo[X]` is newer than the local `shippedTo[X]`: a Ship from elsewhere reached `X` after this config last did (this Machine was offline, or `X` was), so continuing would overwrite a newer config with an older one. The Ship asks, and without a TTY it aborts unless `--overwrite-config` answered in advance. A single global stamp was not enough: a Ship that misses `X` would still advance it, and `X`'s newer config would look older on the next Ship. The copies are stamped before the Ship knows which Machines it will reach, so a copy claims every Machine the Ship planned; only the Starting Machine's own file is rewritten afterwards to claim just the Machines whose config step completed. A copy can therefore over-claim a Machine whose gather succeeded but whose apply failed. That Machine's config was already checked, and overwriting it was already approved if it was newer, so the next Ship from a Machine holding that copy overwrites it without asking again. A second round trip to correct every copy was not worth that one skipped re-prompt. The stamps are not edit timestamps: nothing stamps the file when it is edited.

## Considered Options

- **Config in the user's repo, fleetfizz as that repo's devDependency (ADR 0004, superseded).** It made that repo special: it had to be cloned and installed on a Machine before that Machine could ship, and `pnpm ship` had to run from inside it. With every repo an ordinary Tracked Repo, the config has to live outside all of them.
- **`~/.config/fleetfizz` as a git clone that the Ship fetches and resets (rejected).** History and conflict detection for free, but it needs a config repo, a remote, and the Lent Token on every Machine just to read the config. The config is one small file; copying it is less machinery, and a user who wants history can keep the directory under git themselves without fleetfizz knowing.
- **One global stamp (rejected).** A Ship that cannot reach a Machine still advances the stamp, so that Machine's newer config loses its protection on the next Ship. The per-Machine map costs one key.
- **Stamp the config only when its content changed (deferred).** Simpler to reason about: the stamp is set by every Ship, so every Ship copies the config to every Machine. Reconsider if that line in the Ledger becomes noise.
- **fleetfizz listed in `globals` by the user (rejected).** A listed version can differ from the binary that read the config; the implicit pin cannot.
- **Downgrade a Machine that runs a newer fleetfizz (rejected).** A newer remote means someone shipped a newer version from there; the shipper is the one behind.

## Consequences

- Every Machine in the Fleet can be a Starting Machine as soon as one Ship has reached it: it has vp, fleetfizz, and the config.
- Amends ADR 0001's prerequisites: a remote Machine needs `tailscaled` with SSH, `git`, `curl`, and a shell. vp is no longer a prerequisite.
- Bootstrapping a new Machine is: enable Tailscale SSH, add it to `machines`, Ship.
- The Starting Machine's own config is rewritten by every real Ship (the three stamp keys change). A dry run stamps and copies nothing, and reports the staleness as a note.
- `--config <path>` remains for one-off runs; the upward search from the working directory goes away.
- Machines on the tailnet that are not listed are ignored silently, and a listed name that is not on the tailnet is an error, as today.
